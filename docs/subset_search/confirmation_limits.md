# Confirmation CPU limits and failed attempts

The additional-rounding confirmation keeps the original winner lock, fixed initialization and frozen 50-seed namespace. It does not rerank winners or choose another seed block after an interruption. The separately reserved namespace audit keeps its own timer; each subsequently reserved winner now also installs its declared 120-second process-CPU timer before input verification and rounding. A `finally` block clears that timer and records the actual charge on either success or failure.

Completed confirmations remain `confirmation/confirm-<winner identity>.json`. A failed or timed-out attempt is saved separately under `confirmation/failures/<confirmation ID>/attempt-<timestamp>.json`, preserving configuration, endpoint, first seed, full intended seed list, lock and namespace identities, stage, exception and actual CPU use. The failure record retains partial trials, failed seed and partial predictions exposed by `round_embedding`. If candidate rounding finished before matched-SC rounding failed, its completed trials and predictions are retained too. These are failure artifacts, not completed 50-trial endpoints. A failed attempt cannot leave its own completed confirmation JSON behind.

Failure filenames do not match the root `confirm-*.json` completion scan. The confirmation archive registry includes the entire tree, including failure metadata and nested prediction references. Resuming confirmation uses the same winner and namespace; existing completed endpoints are reused, and prior failure records remain available. The focused fixtures mock rounding, timers and ledger operations; their actual validation result is recorded by the scheduled acceptance job rather than asserted by this implementation note.
