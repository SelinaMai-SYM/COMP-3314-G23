# Final scientific archive and recovery

The prepared archive controller uses the existing two-worker scheduler and shared resource ledger. It calls `export_artifacts.export` and `export_artifacts.recover` without changing their scientific-object format, atomic publication, or verification. It does not load the private data root or fit a model. This document describes prepared execution; it does not establish that the final archive has been exported or recovered.

Stop scientific queues and their launch watchers first. Finalize and commit both `results/submission_refresh/artifact_manifest.json` and `results/subset_search/artifact_manifest.json`. The controller requires their working files to match their exact committed Git blobs, records their SHA-256 hashes and the tested commit, and rejects another active shared reservation. Source files and environment versions are recorded separately. Archive and recovery outputs remain outside Git.

Run `configs/finalization_archive_queue.json` first through the existing `experiments.submission_refresh run` interface, with the campaign configuration and explicit data/artifact roots. Only after that queue has finished, run `configs/finalization_recovery_queue.json` through the same interface. Choose an external `--output` directory for each scheduler invocation; this avoids rewriting the committed scalar snapshot while finalization is being checked. Do not combine the two task lists: recovery must wait for the export record to reach `COMPLETED`.

The export reserves at most 3,600 CPU seconds and recovery at most 1,800, both under phase `aggregation`. Their combined maximum is 90 minutes within the existing two-hour finalization reserve; no new allowance or worker pool is created. The worker guard starts before source or manifest preflight, subtracting whole-worker CPU and cumulative child CPU, with ten seconds held for cleanup. Each local Git child has a remaining-budget wall timeout and CPU resource limit; the worker timer is recalculated after every child is reaped. Wall limits are 7,215 and 3,615 seconds, below the scheduler's termination limits. The returned accounting includes whole-worker process CPU, measured child CPU for short Git checks, wall time and peak RSS. Failed and timed-out jobs, including source-inspection failures, retain their actual status and accounting.

Queue destinations are safe basenames, resolved beside the artifact root: `comp3314-scientific-artifacts-v1.tar.gz` and `comp3314-recovered-artifacts-v1`. Absolute paths, traversal, symlink destinations and existing archive, sidecar or recovery outputs are rejected. A nonblocking destination lock prevents concurrent archive/recovery controllers from racing. Each run has a persistent claim and an external `archive_jobs/<run_id>.json` record; a retry requires a new run ID. Use new destination names whenever a prior attempt published an output. Existing bytes are preserved rather than overwritten.

Recovery requires the exact completed, verified export record, the same committed manifest identities, and unchanged compressed-archive and export-sidecar hashes. It then uses the existing recovery implementation, which verifies members before publishing a new recovered store. The controller does not decompress the archive for an additional preliminary check. A completed recovery records the recovered proof hash and object/file verification counts. A failed export record never qualifies as a recovery dependency, even if it left an atomically published archive before a later provenance check failed.

After both actual jobs finish, inspect the shared ledger, their `task_status` records and the external archive-job records. A concise recovery summary may then be copied into the final scalar publication, including the archive hash, exact manifest hashes, tested commit, recovery proof hash, verified object/file counts and actual CPU use. Fixture tests demonstrate controller behavior only; they do not verify the final scientific archive. Retain the full archive and recovered store in their durable external locations.
